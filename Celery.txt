Chapter - 1: Why Celery Exists
===================================
To handle the tasks that need to be done in background without making the users wait.

Celery is a distributed task queue system that allows your application to hand off long-running or time-consuming tasks to separate worker processes, so the main application can respond quickly without waiting for those tasks to finish.


Chapter - 2: What Exactly is a Task?
=======================================

A Celery task is a normal Python function that Celery wraps with additional information so it can be executed by a worker.

Normal Function -> Celery adds metadata -> Now it becomes a Task



Python function -> Celery packaging -> Task ID, Queue Name -> Arguments -> Retry information -> Celery Task

@app.task
def send_email(user_id):
    print("Email Sent")
    
@app.task decorator, will tell that need to be done in background whenever it was asked. So, remember that. 

Polished answer,
Adding @app.task does not execute the function in the background. It simply registers the function as a Celery task, making it eligible to be executed by a Celery worker later. The task will only run asynchronously when we explicitly send it to Celery (for example, using delay() or apply_async()).

Chapter - 4: What Exactly is a Celery Worker?
===============================================

A Celery worker is an independent operating system process.

When you run:
celery -A config worker

The OS creates a new process.

So, if suppose we have only one worker and it was running one task which takes 10mins. And there other two python functions to run. Until that task is done, these two need to be wait. Here, we will get bottle neck. So, Celery create child processes.


A Celery worker is a main process that can manage one or more child processes to execute tasks concurrently.


Imagine this.

Celery Worker (Main Process)

        │

 ┌──────┼──────┐

Child1  Child2  Child3

Now:

Child1 → Email

Child2 → PDF

Child3 → SMS
Three different tasks execute simultaneously.

Notice something important.

We still say:

"One Celery Worker"

But internally,

that worker can manage multiple child processes.

This is called worker concurrency.

A Celery worker with a concurrency of 4 can execute up to 4 tasks simultaneously because it creates 4 child processes (using the default prefork pool). Each child process can execute one task independently.


celery -A config worker --concurrency=4

This command will create four child processes to the Celery worker (main process)


Increasing concurrency, will waste the resources leads to context switching which wastes the time, more swithcing, more overhead, and less useful work.

Chapter - 14: When Does Celery Send the ACK?
==============================================
There can be at-most-once delivery. What happens if we immediately send ACK after taking task.

There can be duplicate execution. When same task repeats because of crashing of worker before sending ACK. It was better than above. But not ideal. Because, at banking system, two payments can be done for the same user if he did only one time. Because of this.

So, engineers think about Trade-offs not perfection.

But, celery most lean toward option b. Because losing task is more critical than repeating a task.

The real solution is to make the task itself safe to run more than once, or otherwise ensure duplicate execution doesn't produce incorrect results.

That concept is called idempotency.

Ex:
Think:

"If it runs twice, does it produce a different final state?"

If the final state is the same, it's a good candidate for being idempotent.




Chapter 15 – If Every Task Has a Task ID, Why Can Duplicate Execution Still Happen?
====================================================================================

Because it don't know whether that task was done or not to another worker. So, we need to write safe logic. So, that even if same task we need to handle that.

If an interviewer asked:

"Would you make send_welcome_email idempotent?"

A balanced answer would be:

"It depends on the business requirements. If duplicate emails would significantly affect user experience or brand perception, I would make it idempotent. Otherwise, I might accept the small possibility of duplicate emails to keep the system simpler, while ensuring business-critical tasks like payments are always idempotent."

That answer shows you're making decisions based on impact, not applying the same solution everywhere.


A Principle to Remember

The stronger the business impact of duplicate execution, the stronger the need for idempotency.

Examples:

Task			Duplicate Execution Impact	Usually Make Idempotent?
Deduct money		🚨 Very High			✅ Always
Create invoice		🚨 Very High			✅ Always
Ship order		🚨 Very High			✅ Always
Award loyalty points	🚨 High			✅ Usually
Send welcome email	🙂 Low				Depends
Write a log entry	😀 Very Low			Usually not necessary

Chapter 22 - Immutable Signatures (.si())
=============================================

We learned that ouput of one task will be input of another task. But, what if in that function definition we only have one argument. But while it was passing it became 2. Now, python raise TypeError with number of arguments this function receives.

Celery says:

"Sometimes you don't want the previous task's result."

So it provides an Immutable Signature.

So, insted of .s() we will write like .si()

Ex:

@app.task
def say_hello():
    return "Hello"
    
@app.task
def cleanup():
    print("Cleaning temporary files...")
    
chain(
    say_hello.s(),
    cleanup.si(),
)

'i' stands for immutable. Means Do not modify my arguments

Mental Model

Think of .s() as saying:

"I'm willing to receive whatever the previous task returns."

Think of .si() as saying:

"Leave my arguments exactly as they are."

Chapter - 32: Exponential Backoff
=======================================
It means increasing the delay time in the retries. Instead of constant time, like 5 sec betweeen every retry. We increase that value like 5, 10, 20, 40, 80 like that seconds.

So, whatever the server we are hitting will have time to recover and handle our requests later.


Chapter - 33: Jitter
==========================

If suppose, we have 5000 workers using exponential backoff. All will again hit the server at a time. Even though we have space for the server to available. So, it will be again come to original problem.
So here comes the Jitter.

It's like starting workers in different times by making difference in delay times. So that, workers will not start at a time. So that, it can get accepted by service and get the thing to be done.


Each layer solves a different problem:

Retry → Gives temporary failures another chance.
max_retries → Prevents endless retry loops.
Exponential backoff → Gives the external service time to recover.
Jitter → Prevents thousands of workers from retrying at exactly the same time.

Chapter 46 - Prefork Pool (The default pool)
===============================================
The word Prefork can be split into two parts:

Pre + Fork
	Fork means creating a new process (on Unix-like systems).
	Pre means it creates those processes before tasks arrive.

So when the worker starts, it immediately creates child processes that are ready to execute tasks.



Chapter 47 - Thread Pool
=============================
Instead of creating multiple child processes like Prefork pool, it will create multiple threads which are lightweight.

celery -A project worker --pool=threads --concurrency=4

It is best for I/O-bound tasks.

Because, of GIL

Python has something called the Global Interpreter Lock (GIL).
- The GIL allows only one thread at a time to execute Python bytecode within a single Python process.

- Because of this, CPU-intensive Python code generally does not gain true parallel execution from multiple threads.

- That's one of the main reasons Celery uses Prefork as the default pool for CPU-heavy workloads.



Chapter 48 - Gevent Pool
==============================

Gevent is a worker pool designed for high-concurrency I/O bound tasks.

Like waiting for API, DB's, pdf upload like those.

celery -A project worker --pool=gevent --concurrency=1000


- Instead of processes, threads they are called as greenlets.



Chapter 49 - Eventlet Pool

Celery automatically sends tasks to the correct queue based on rules you define.

send_email.delay()

    },

        "queue": "payment",
    },
    "images.tasks.resize_image": {
        "queue": "image",
    },
}

=====================================

Graceful Shutdown means:

Chapter 60 - Warm Shutown v/s Cold Shutdown
=============================================
Warm Shutdown means:

	Finish the currently running tasks and then exit.
	
	
Cold Shutdown means:

	Stop immediately without waiting for running tasks to finish.

Best Practices

✅ Use warm shutdown before restarting.

✅ In production, restart workers one by one (rolling restart) instead of stopping all workers together.

Module 1: Introduction to Celery Beaat

Chapter 62 - What is Celery Beat?
============================================

Suppose your company says:

Every day at 12:00 AM, generate yesterday's sales report.

Who will call:

generate_sales_report.delay()
at exactly 12:00 AM?

There may not even be any users using the website at that time.

So who starts the task?


Answer is Celery Beat.

Celery Beat is a scheduler. It doesn't execute tasks. It only decides it's time to run this task. Then it sends the tasks to RabbitMQ and workers execute it.

celery -A config beat



Chapter 63 - Periodic Tasks
=============================

But one question remains.

How does Celery Beat know WHEN to send the task?

The answer is:

CELERY_BEAT_SCHEDULE

What is CELERY_BEAT_SCHEDULE?
It is a dictionary in settings.py that tells Celery Beat:

Which task to run

When to run it

Think of it as Beat's timetable.


Ex:

# tasks.py

from celery import shared_task

@shared_task
def say_hello():
    print("Hello from Celery Beat")
    

In settings.py,

from celery.schedules import crontab

CELERY_BEAT_SCHEDULE = {
    "say-hello-every-minute": {
        "task": "myapp.tasks.say_hello",
        "schedule": 60.0,  // Run for every 60 seconds. If for five minutes it will be 300.00
    },
}


Multiple Scheduled Tasks
CELERY_BEAT_SCHEDULE = {

    "send-email": {

Chapter 69 - Control Commands
===============================

In last chapter we learnt commands for observing. Now, we will learn how to control them

Basic Syntax
celery -A config control <command>


Command 1 — Shutdown

Suppose you have:

Worker A

Worker B

Worker C

Command:

celery -A config control shutdown

Result:

Worker A

↓

Shutdown

----------------

Worker B

↓

Shutdown

----------------

Worker C

↓

Shutdown

All workers receive the shutdown command.

Remember from the Worker Lifecycle chapter:

Normally this performs a graceful (warm) shutdown, allowing running tasks to finish before exiting.



Command 2 — Revoke

This is one of the most useful commands.

Suppose a task is waiting.

RabbitMQ

↓

send_email()

↓

Worker

Suddenly your manager says:

Don't send that email.

If you know the task ID, you can revoke it.

Syntax:

celery -A config control revoke <task_id>

Example:

celery -A config control revoke 8d0d7f9d...

Meaning:

Don't execute this task.




Revoke depends on the state of that task
- If that task not started, then after marking it as revoke. No worker take that task.
- If the task is running, it will be marked as revoke. But by default, the running task is usually allowed to finish.

To terminate it completely of the running task, we need to force it.

celery -A config control revoke \
<task_id> \
--terminate

This sends a termination signal to the worker process executing that task.

⚠️ Use this carefully because the task may stop in the middle of its work.




Chapter 70 - Purging Queues
===============================
Scenario: No worker has taken them yet.

Now your manager says:

These tasks are wrong. Delete them all.

How do you do that?

The answer is:

Purge the Queue


Purge means: Delete all pending tasks from the queue.

celery -A config purge


When Should You Use Purge?
Good situations:

	Wrong tasks accidentally queued.

	Testing environment cleanup.

	Development environment cleanup.

	Bug discovered before execution.


Comparison
Purge				Revoke
Deletes all pending tasks	Cancels one task
Works on the queue		Works using a task ID
Very dangerous			More targeted
Used rarely			Used more often

Chapter 74 - Task Events & Worker Events
============================================
But one question remains:

How does Flower know that a task started, succeeded, or failed?

The answer is:

Events



An event is simply a notification sent by Celery. 


There are two major categories.

a) Task Events: These tell what happened to a task.

Task received, started, retry, success, failure, revoked


b) Worker Events: These tell what happened to a worker.
Worker online, worker offline and worker heartbeat.

Worker heartbeat - Every worker periodically tells the system:
	I'm Alive
